INSTRUMENTATION ADDED / FAILURE LOG SCHEMA
Exactly one northbridge.readiness WARNING event per normal non-200 readiness response. No new success INFO or DEBUG event. Existing generic HTTP logging remains unchanged.
Top-level JSON fields:
  event: readiness_failed
  timestamp: UTC ISO 8601
  request_id: generated random UUID hex; no user/session identifier
  status_code: 503
  duration_ms: elapsed readiness endpoint time until failure diagnostics are assembled
  components: one detail object for each of the four required components
Every component: status, duration_ms, failure_type.
I/O components also: queue_ms, task_age_ms, execution_state, exception_type.
duration_ms measures execution in the thread; for a running task it is elapsed execution, not completed latency. Before execution it is zero, with queue_ms showing elapsed queue time. task_age_ms includes queue time and can predate the current request when an in-flight task is reused. Completed timings persist alongside their matching task until replacement. NOC timing measures only the flag check.
failure_type:
  null — component ok
  not_ready — false NOC flag
  component_timeout — recognized dependency timeout exception
  exception — other exception from the component
  shared_deadline_exhausted — task is still pending when the existing decision evaluates it; execution_state distinguishes queued from running
  unavailable — canceled task or unclassified unavailable state
The wait does not itself cancel a task. Explicit cancellation is logged as canceled/unavailable, not misrepresented as deadline-triggered cancellation. Shared-deadline classification describes the observed pending state; it does not prove why that task was slow. Pre-existing overlapping-task evaluation behavior can also contribute to that state.
No exception message, traceback, result, URL, connection string, bucket name, credentials, API key, JWT, token, header, cookie or user information is copied into this event. Exception classes are allowlisted by exact module and class name. Unknown/custom classes become the literal Exception. A class whose name contains sensitive information is covered by a leak test.
Logging/handler exceptions are contained so they cannot replace a readiness response. That safeguard can lose a diagnostic event if logging itself fails; it never changes health. Normal failure logging is synchronous, so a blocked log destination can add failure-path latency; healthy requests do not invoke it.

CORRELATION METHOD
Readiness-only resolve_request_id generates a UUID regardless of an inbound X-Request-ID. The existing observe_request middleware stores it on request.state, returns it in the existing X-Request-ID header and uses it in existing generic request logs. The failure warning uses that same ID. No new response field/header is introduced. Matching a private captured 503 header to the readiness_failed event is exact; generic HTTP completion logs share the ID where INFO logging is collected. Bare Uvicorn access lines do not contain this ID and require timestamp/status correlation.
Other paths preserve existing caller-supplied request ID handling; this has an explicit regression test. Readiness callers can no longer prescribe its request ID. This intentional diagnostic correlation change does not alter status, payload, probes, timeout or required components.
